# Mumbai deployment

This template provisions one isolated hospital environment in ap-south-1: two-zone networking, private Fargate web/worker tasks, TLS load balancer, separate encrypted Multi-AZ clinical and erasure-ledger PostgreSQL instances, 35-day PITR retention, patient-key KMS custody, separate runtime/migration execution roles, Secrets Manager placeholders, 180-day application logs and operational alarms. No cloud resources are created by the tests.

Run each hospital/environment with its own encrypted, access-controlled remote state and distinct AWS credentials/accounts where possible. Do not reuse state between staging and production. State location and cloud account configuration belong to the deployment operator. Terraform stores infrastructure metadata; this template never reads secret values or takes plaintext database passwords as inputs.

1. Build, scan and verify immutable backend/frontend image digests. Images in the account's ECR use the execution role; public registries also work. Private external registries require registry_credentials_secret_arn pointing to username/password JSON. Add its customer KMS key ARN to secret_kms_key_arns if necessary. Issue the regional ACM certificate for the hospital domain.
2. Copy hospital.tfvars.example into an ignored file, replace its values and keep desired_count=0. Run terraform init, terraform validate and terraform test. Review a real terraform plan before applying from your own cloud account. The local mocked plan does not establish quota, cost, permissions or service availability.
3. Bootstrap both private databases from an approved operator task/client. Use the RDS-managed owner credentials initially, create a separate clinical migration owner and a restricted application role, run backend migrations, then apply deploy/runtime-grants.sql. Apply deploy/erasure-ledger.sql to the independent ledger; the application ledger login gets SELECT only, and the erasure operator gets SELECT/INSERT without ownership or trigger privileges. The migration task definition is a one-off runner, not an automatically launched service.
4. Populate the runtime secret's JSON keys: DATABASE_URL (restricted clinical login), JWT_SECRET, ENCRYPTION_KEY (32-byte base64), MSG91_AUTH_KEY, MSG91_FLOW_ID, ADMIN_USER_IDS, ERASURE_LEDGER_DATABASE_URL (read-only ledger login), DB_CA_PEM (trusted RDS regional CA bundle, public certificate material). Provision the administrator phone identity using bootstrap-admin.js with operator database credentials, then set its stable user UUID in ADMIN_USER_IDS. Use the separate migration secret for DATABASE_URL and DB_CA_PEM. Use an independently managed migration login rather than copying a rotating RDS master password into a static URL. Secret values are supplied by the operator and never committed.
5. Verify both schemas, grants, independent ledger gate, provider-approved SMS flow and KMS permissions. Set desired_count=2; map the hospital hostname to load_balancer_hostname. Subscribe the hospital's on-call destination to alert_topic_arn using its approved process. This template does not send messages or create subscriptions. Rehearse alerts, backup/restore and failover in staging before a real-patient release.

The API is reachable only through the frontend sidecar and ALB; no public database/task IP or SSH port is created. The frontend trusts only the VPC proxy range, and Express trusts the two configured forwarding hops. Readiness is checked through /api/ready before traffic. Application logs contain route templates and counts, not clinical bodies. ALB access logging is deliberately not enabled because raw request paths could contain patient identifiers. Review any additional logging services before enabling them.

KMS context uses the non-sensitive deployment slug, never a patient identifier. The application role has Encrypt/Decrypt on the patient CMK; the operator role adds rewrap permissions and cannot be assumed by the running app. Automatic CMK rotation preserves decryption. Manual key replacement requires an approved migration of historical envelopes before removing old CMKs. rewrap-aws-keys.js --apply supports local-wrapped keys and AWS KMS rewrap with compare-and-swap updates; do not retire a legacy key until decryption and restore checks pass. Vault-to-AWS custody conversion remains an explicit operator migration, not an automatic cutover.

AWS initialization, secret provisioning, domain/certificate validation, real alert delivery, container/image scan execution and measured RPO/RTO remain deployment acceptance evidence. Terraform validate/mock tests are not a deployed-system test. Keep deletion protection enabled; deleting these resources requires the operator's separate retention and exit process.
